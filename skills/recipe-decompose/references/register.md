# Round 3: Linear Registration

## Step 1: Verify Linear MCP Availability

Check Linear MCP connection by invoking `list_teams`.

- If successful: proceed with registration (Step 2).
- If failed: report the missing required dependency and stop without creating or drafting issues.

## Step 2: Determine Target Context

Identify team and project for issue creation:

- If the input was a Linear issue URL, use the same team and project as the source issue.
- If the input was a file, ask the user: "Which Linear team should these tasks be created in?" Use `list_teams` to present available options.
- If a project context is appropriate, ask: "Associate these tasks with a Linear project? (provide project name or skip)"

## Step 3: Create Parent Issue (PRD-based input only)

When the input was a file (PRD or requirement document), create a parent issue before registering tasks:

1. Create a Linear issue with:
   - **Title**: The PRD title or extracted objective from `$ANALYSIS`
   - **Description**: One-paragraph summary of the requirement scope and the number of sub-tasks to be created.
   - **Team**: determined in Step 2
   - **Project**: determined in Step 2 (if specified)

2. Record the parent issue identifier as `$PARENT_ISSUE_ID`.

When the input was a Linear issue URL, the source issue serves as the parent. Record its identifier as `$PARENT_ISSUE_ID`.

## Step 4: Register Issues

For each task in `$FINAL_TASKS`, in dependency order:

1. Create a Linear issue using `create_issue` with:
   - **Title**: `[task_id] title` (e.g., "[T1] Define shared API contract")
   - **Parent**: `$PARENT_ISSUE_ID`
   - **Description**: Markdown formatted:
     ```
     **Goal**: observable condition that proves task completion

     **Task Type**: task_type
     **Affected Services**: comma-separated list

     **Service Scopes**:
     - service: scope

     **Dependencies**: depends_on list with task IDs and titles
     **Dependency Notes**:
     - dependency_notes entries

     **Assumptions**:
     - task.assumptions entries (omit section if empty)

     **Key Decisions**:
     - task.key_decisions entries (omit section if empty)

     ---
     _Generated by linear-prism recipe-decompose_
     ```
   - **Team**: determined in Step 2
   - **Project**: determined in Step 2 (if specified)

2. Record the returned issue URL and identifier.

3. After all issues are created, set blocking relations:
   - For each dependency edge, set a blocking relation on the dependent issue (using the `blockedBy` parameter) pointing to the dependency-source issue.
   - `blocking_issue_id` refers to the Linear issue identifier of the dependency-source task, not the parent issue.

## Step 5: Present Registration Results

Display a summary table:

```
| Task ID | Title | Linear Issue |
|---------|-------|-------------|
| T1 | Define shared API contract | ENG-456 (URL) |
| T2 | Implement submission flow | ENG-457 (URL) |
```

State: "Registration complete. X issues created in [team name] under [parent issue identifier]."

## Step 6: Stop

Registration is the final step. The orchestrator stops here.
